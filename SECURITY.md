# Modrik security setup and operational boundary

> **Current status (H1):** the historical Phase 0–1 notes below are retained for design traceability, but later H1 sections supersede earlier single-owner / pre-RBAC statements. The current code enforces database-backed identity sessions, organization membership and tenant-scoped route permissions. Production rollout remains blocked on the migration-baseline and live-provider/restore gates in [docs/security-deployment.md](./docs/security-deployment.md).

## Authentication and organization access

The current H1 branch implements **multi-user identity and organization/project authorization**: signed identity sessions, database-backed membership checks, role-specific permissions, tenant isolation, invitations, password recovery and a shared rate limiter. This is not a replacement for enterprise SSO/MFA, and it is **not production-cleared** until the database baseline, live provider connectivity and backup/restore gates below are verified. Application pages and API routes are protected by the Next.js 16 `proxy.ts` boundary, except the narrowly scoped authentication endpoints and the public study participant page/write endpoint. Those two study paths expose no session listing or export; the write endpoint requires a high-entropy per-session bearer token, applies metric bounds and rate limits, expires after seven days, and becomes write-locked after finish except for withdrawal. The API boundary is enforced server-side; hiding UI controls is not relied upon.

Set these variables before deploying:

| Variable | Required | Meaning |
| --- | --- | --- |
| `MODRIK_ADMIN_EMAIL` | Yes | The one administrative account |
| `MODRIK_ADMIN_PASSWORD_HASH` | Yes | Scrypt hash generated by `node scripts/hash-admin-password.mjs` |
| `MODRIK_AUTH_SECRET` | Yes | At least 32 random bytes, used to sign 8-hour HttpOnly sessions |
| `MODRIK_ENCRYPTION_KEY` | Yes for saved integrations | 32-byte base64 or 64-character hex key for AES-256-GCM |
| `MODRIK_JIRA_ALLOWED_ORIGINS` | Optional | Comma-separated exact HTTPS origins for approved self-hosted Jira instances |

Generate independent high-entropy secrets; never reuse the session-signing key as the encryption key. Keep them in the deployment secret manager, not in Git.

Example key generation (run locally and store the output securely):

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
node scripts/hash-admin-password.mjs
```

For local development, add the generated values to the ignored `.env` file. The application intentionally fails closed with HTTP 503 when authentication is not configured. It must not be exposed publicly with missing auth settings.

## Session controls

- Public study routes are narrowly scoped: `/study/participant` is a generic form, while `/api/study/respond` accepts only a session-specific bearer token. Study dashboard, session creation, moderation, and CSV export stay owner-authenticated.
- Study participant tokens are random 256-bit secrets. Only a SHA-256 hash is stored; the raw token is returned once at moderator session creation and should be handed to the participant over a separate trusted channel. Tokens expire after seven days. After a participant finishes, only withdrawal remains allowed until token expiry; withdrawal scrubs measurements and session events and revokes the token.
- Eight-hour signed sessions, HttpOnly, SameSite=Strict cookies, Secure in production.
- Login, password recovery, invitation creation and invitation acceptance use an atomic Redis fixed-window limiter when `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are configured. Identifiers are SHA-256 hashed before becoming Redis keys.
- Production authentication and invitation flows fail closed when the shared limiter is missing or unavailable; configure Upstash before rollout. Development/test can use a bounded process-local fallback only.
- Rate-limit ingress identity must come from trusted proxy headers. The ingress must overwrite `X-Real-IP` and `X-Forwarded-For`; never trust arbitrary client-supplied forwarding headers.
- State-changing requests with an explicit cross-origin Origin are rejected. The origin check compares against the incoming request Host and the ingress-provided `X-Forwarded-Proto` (when present), rather than Next.js' internal URL origin; the reverse proxy must overwrite forwarded headers. Requests without Origin are rejected when Fetch Metadata marks them cross-site.
- Security response headers include frame denial, MIME sniffing protection and a restrictive referrer policy.
- The proxy validates identity and organization membership, while route-level policy checks enforce organization and project permissions. New API handlers must be explicitly classified and covered by authorization regression tests.

## Integration credential storage

New GitHub/Jira tokens are stored with AES-256-GCM authenticated encryption. Legacy plaintext tokens remain readable to avoid silently breaking an existing installation; re-save each integration after configuring `MODRIK_ENCRYPTION_KEY` to migrate it. Existing plaintext database values are **not** automatically rewritten during read operations.

Jira URLs are restricted to official Atlassian Cloud tenant hosts or exact HTTPS origins explicitly allowlisted by the deployment operator. Redirects are disabled for Jira API calls to prevent an approved endpoint from redirecting credentials to another host. Do not add untrusted origins to the allowlist.

Tracker push retries use a local per-item reservation plus a stable marker on the remote GitHub Issue/Jira issue, and search for that marker before creating a replacement. This provides best-effort duplicate recovery after common timeout or local-persistence failures; it is not a distributed exactly-once guarantee because external search indexing and issue creation are controlled by the tracker provider. Reconcile ambiguous failed pushes against the remote tracker before manually retrying them.

## Project audit export

The project decision journal can be exported as JSON or CSV through `GET /api/projects/{projectId}/audit/export`. The route requires the explicit `audit:read` permission, is project-scoped, returns no-store responses and caps each export at 10,000 records. CSV cells are quoted and spreadsheet formula prefixes are neutralized. Engineer and Viewer roles do not receive audit export access.

## GitHub webhook ingress

Project-scoped GitHub webhook ingress is exposed only at `POST /api/webhooks/github/{projectId}`. Configure Issues and Push events and store a random secret (minimum 32 characters) in the GitHub integration settings. The secret is encrypted at rest; the endpoint verifies `X-Hub-Signature-256` over the exact raw body, binds the event repository to the saved owner/repository, bounds payload size and deduplicates delivery IDs. It accepts no browser session; the HMAC signature is its authentication boundary. Never expose the endpoint without a configured secret or weaken the exact route/method exemption in `api-access.mjs`.

## Evidence processing consent and schema rollout

The evidence consent checkbox is an explicit permission flag for sending that source's text to the configured AI provider. Unchecked sources remain in the private project library but are filtered out of planner, extraction, verification, and memory-generation prompts. A client-supplied `"false"` string is rejected; consent must be a real boolean. Synthetic Wind Tunnel answers are marked with their own provenance and never count as human stakeholder answers.

Evidence codes are stable identifiers, not list positions. Deleting a cited source removes its trace links and moves affected requirements back to revised/unverified review. It does not renumber remaining sources. Existing `TraceLink` rows are attached to `Evidence` by their new optional `evidenceId` as new trace links are created; legacy code-only links are handled during deletion.

Phase 1 adds schema relations for project-scoped memory and stable evidence trace IDs. Back up the database before applying the schema update. For local SQLite run `bun run db:push`; for PostgreSQL run `bun run db:push:pg` with the production `DATABASE_URL` set. These commands intentionally do not use Prisma's destructive `--accept-data-loss` flag.

## Identity and organization foundation (H1.2)

The identity schema introduces three distinct concepts:

- `User` is an authentication principal with a unique normalized email and an explicit active/disabled state.
- `Organization` is a tenant boundary.
- `Membership` connects one user to one organization and carries one of six roles: `owner`, `admin`, `engineer`, `reviewer`, `approver`, or `viewer`. Membership status is explicit: `invited`, `active`, `suspended`, or `revoked`.

Stakeholder profiles remain project-domain records. They are not users, cannot authenticate, and their influence/approval metadata does not grant application permissions.

Project `organizationId` and `createdByUserId` are intentionally nullable in this additive schema slice. Existing projects are not silently assigned to a guessed tenant or account. A later, explicit backfill must establish an owner organization before tenant-scoped access is enabled.

The pure policy in `src/lib/security/organization-access.mjs` defines the fail-closed permission matrix and tenant-ID comparison. It is wired into identity-backed sessions and route authorization in the subsequent H1 slices. Organization-level control is owner-only; admins can manage members and projects but cannot change organization ownership/settings. The presence of schema tables alone is not the security guarantee: the proxy, session revalidation and route-policy checks are the enforcement boundary.

## Identity-backed sessions and tenant authorization (H1.3)

Identity sessions are signed, short-lived cookies backed by an `AuthSession` row. The database stores the session identifier, user, membership, expiry and revocation timestamp; it never stores the raw cookie token. Every protected request re-resolves the session and checks that the user, organization and membership are still active and that the signed claims still match the database records. Logout revokes the database session.

The configured bootstrap administrator is provisioned into the default `Modrik Workspace` on successful login. Existing unassigned projects are adopted only into that bootstrap organization; projects already assigned to another organization are never reassigned. New project and mission/demo creation stores the trusted organization and creator context injected by the server proxy. Project lists, mission catalogs, demo lookup and telemetry aggregates are tenant-scoped. Project API routes enforce same-tenant access and role permission before reaching route handlers.

Identity context headers (`x-modrik-user-id`, `x-modrik-organization-id`, `x-modrik-membership-id`, `x-modrik-role`) are stripped from incoming requests and injected by the proxy only after a database-backed session is validated. Application code must never accept caller-supplied values as identity.

The current bootstrap flow provisions the configured administrator. Invited-user onboarding and password recovery are implemented in H1.7–H1.8. Organization switching, MFA/SSO and distributed session/rate-limit infrastructure remain follow-up work. Do not expose self-service registration or treat the current bootstrap path as a complete identity lifecycle.

## H1 release validation and production configuration (H1.10)

Run `bun run security:release-check` in the deployment environment before release. The check validates the presence and format of PostgreSQL, administrator bootstrap credentials, a 32-byte session signing secret, a 32-byte AES-256-GCM key, HTTPS Upstash Redis REST configuration, Resend sender configuration, and the canonical HTTPS application URL. It reports variable names and validation failures only; it never prints secret values. CI runs the same check against disposable placeholder values. A passing shape check does not prove provider credentials are active: verify Redis connectivity, Resend sender/domain verification, database backup/restore, and deployed health checks as an operational release step.

## Distributed rate limiting (H1.9)

- Configure `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` with an HTTPS Upstash Redis REST endpoint.
- The limiter uses a single atomic Lua fixed-window increment/expiry operation. It does not downgrade to process-local memory in production when Redis is missing or unavailable.
- Login is limited by source IP and normalized account identifier. Password recovery is limited by source IP and account. Reset completion and invitation acceptance are limited by source IP; invitation creation is limited by organization and inviter.
- Identifiers are hashed before storage in Redis. API responses include `Retry-After` for explicit 429 responses and never expose the identifier or Redis key.
- The local memory fallback exists for development/test only and is bounded. It is not a production security boundary.

## Password recovery (H1.8)

- Public recovery requests use a generic response for unknown, disabled, and eligible accounts to reduce account enumeration.
- A configured Resend sender and trusted application URL are required. Set `RESEND_API_KEY`, `PASSWORD_RESET_EMAIL_FROM`, and `APP_URL`; recovery remains disabled with HTTP 503 until all are configured.
- Reset links carry a random 256-bit token, while only its SHA-256 digest is stored. Tokens expire after 30 minutes, are single-use, and are revoked after a successful reset.
- Password reset revokes every active session and every other outstanding reset token. The user must sign in again.
- Delivery failures revoke the newly created token. The endpoint does not return reset URLs to callers or log bearer tokens.

## Current boundary and next security phase

This phase does not claim full legal compliance or a completed penetration test. Organization-scoped authorization and application-level distributed rate limits are implemented, but production rollout still requires provider configuration and operational verification. The following remain required before production rollout and before claiming enterprise-grade security:
- provider-specific database baseline reconciliation, verified backup/restore and controlled migration execution;
- live Upstash Redis and Resend connectivity checks plus production HTTPS/cookie verification;
- broader authorization tests for every background job and any future API surface;
- MFA/SSO and centralized security event monitoring;
- auditable retention, erasure, consent purpose and processing-provider policies;
- independent penetration testing and security review.

The system must not process stakeholder evidence using an external model unless the applicable project processing policy permits that provider. Consent fields alone do not establish legal compliance.


## Non-project API authorization (H1.4)

Identity-backed requests to non-project API handlers require an explicit organization permission in `src/lib/security/organization-route-access.mjs`. Unknown paths or methods fail closed with `403 API_ROUTE_NOT_CLASSIFIED`; adding a new API handler therefore requires an explicit policy and a regression test.

| Route | Methods | Required permission |
| --- | --- | --- |
| `/api` | GET, HEAD | `organization:read` |
| `/api/transcribe` | POST | `requirements:write` |
| `/api/missions`, `/api/demo` | GET, HEAD | `projects:read` |
| `/api/missions`, `/api/demo` | POST | `projects:create` |
| `/api/telemetry` | GET, HEAD | `audit:read` |
| `/api/study` | GET, HEAD, POST, PATCH, DELETE | `organization:manage` |
| `/api/self-audit` | GET, HEAD | `organization:manage` |
| `/api/providers` | GET, HEAD | `organization:read` |

The unauthenticated API surface is method-specific: `POST /api/auth/login`, `POST /api/auth/invitations/accept`, `POST /api/auth/password-reset/request`, `POST /api/auth/password-reset/complete`, `POST /api/auth/logout`, `GET /api/auth/session`, and participant-scoped `GET|POST /api/study/respond`. A path-only match is not sufficient to bypass authentication.

All `/api/projects/*` handlers are separately checked for project existence, organization ownership and the route's project permission before the handler runs. The route inventory test scans every API `route.ts` file and fails when a newly added method is neither an exact public exemption, a project-scoped handler, nor explicitly classified.

This is a technical access-control gate, not a completed enterprise security review. MFA/SSO, route-level penetration testing and production migration rollout remain separate release gates.

## Benchmark integrity gate (H1.4)

CI validates all 120 `arbench-v2` scenarios before a change can pass. Validation checks manifest count, unique stable IDs, the 8-category × 5-domain × 3-scenario coverage matrix, scenario-file presence and JSON validity, manifest/file metadata parity, gold payload presence, and evidence-code/consent integrity. This is a corpus-integrity check; it does not claim model-quality scores or execute paid/provider-backed inference.


## Jira webhook ingress

- Endpoint: `POST /api/webhooks/jira/{projectId}` (HTTPS only in production).
- Configure the Jira Cloud project integration and set a high-entropy webhook secret (at least 32 characters) in the project integration console. The secret is encrypted at rest and is never returned to the browser.
- In Jira Cloud, create an admin webhook for `jira:issue_created`, `jira:issue_updated`, and `jira:issue_deleted`, using the same secret. Jira signs the raw request body in `X-Hub-Signature` using the declared HMAC method; Modrik currently accepts SHA-256 and rejects malformed or mismatched signatures.
- Modrik requires `X-Atlassian-Webhook-Identifier` for retry deduplication, checks the event's project key against the configured project, enforces a 1 MB payload cap, and returns a retryable 5xx only when drift processing fails.
- Test a real delivery after deployment. Automated tests cover signature verification, ADF description normalization, project isolation and unsupported events, but do not prove external delivery or Jira-side configuration.
