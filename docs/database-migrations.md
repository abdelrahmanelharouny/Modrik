# Database evolution and migration safety

## Current state (H1.6)

Modrik has one canonical Prisma data model at `prisma/schema.prisma` (SQLite). The PostgreSQL schema is generated by `scripts/sync-postgres-schema.mjs` and differs only in the datasource provider. CI validates both providers, generates both Prisma clients, validates both schemas, and pushes the schema to disposable CI databases.

**Important:** the repository currently has no committed Prisma migration history. Existing environments may have been provisioned with `prisma db push`. Do not run `prisma migrate deploy` against an existing database until a reviewed baseline has been created and reconciled with that database. An empty migration directory is not a safe substitute for a baseline.

## H1.5–H1.6 safeguards

- `bun run db:sync:pg` deterministically regenerates `prisma/schema.postgres.prisma`.
- `bun run db:validate:parity` rejects any model/field/index drift between the canonical SQLite schema and generated PostgreSQL schema.
- `bun run db:inventory:write` refreshes `prisma/schema-inventory.json` with deterministic SHA-256 fingerprints and model inventory for both provider schemas.
- `bun run db:inventory:check` verifies the committed inventory in CI; it describes repository schemas only, not any deployed database.
- `bun run db:push` and `bun run db:push:pg` remain schema-prototyping/CI operations, not a production migration strategy.
- Pull requests validate SQLite and PostgreSQL independently. CI database pushes target disposable databases only.

## Required migration rollout before production adoption

1. Inventory every deployed database and record provider, schema fingerprint, migration history table presence, backup timestamp, and row counts for critical tables.
2. Freeze schema changes and take a restorable backup. Test restoration, not merely backup creation.
3. Generate provider-specific baseline SQL from the exact reviewed schema for SQLite and PostgreSQL. Review destructive statements and provider-specific differences manually.
4. Reconcile each existing database with the baseline. Mark a baseline as applied only after structural equivalence has been independently verified; never use `migrate resolve --applied` as a shortcut before verification.
5. Commit versioned migration artifacts and a checksum/manifest. Every future schema change must be an additive, forward migration where practical; destructive cleanup follows a separate expand/contract release.
6. In CI, create empty databases and upgrade from the previous migration to head for both providers. Also test an upgrade fixture containing representative pre-existing rows.
7. Deploy migrations once in a controlled release job using a single-writer lock. Application startup must not mutate production schemas.
8. Verify post-deploy schema fingerprints, referential integrity, critical row counts, application health and rollback/restore readiness.

## H1.6 release controls

- `bun run db:migrate:deploy` is a fail-closed entry point and refuses to run until a provider-specific baseline and deployment acknowledgement exist.
- No production migration history is fabricated from the Prisma model. The inventory manifest is not evidence of deployed schema equivalence.

## Release blockers

- No production migration runner is enabled yet.
- No baseline is committed because the deployed database histories have not been reconciled.
- No automatic schema mutation should be added to the application boot path.
- SQLite and PostgreSQL migration SQL must be generated and tested separately; do not assume a single SQL file is portable.

This gate intentionally prefers a visible release blocker over silently adopting an unknown production database state.
